## The problem

Reporting an incident online meant photographing evidence and hoping the right department saw it.
Files were sent over chat apps and email, arrived out of context, and there was no record of who
handled them or when.

The brief was a channel where a citizen submits evidence directly to a police department, where
staff can review and respond, and where every action is recorded.

## What I built

A Django application built around one principle: evidence is sensitive, and every design decision
followed from that.

**Evidence upload and management** — users upload images, video, audio and documents, organised
with titles, descriptions and timestamps so an item is identifiable months later.

**Secure submission to police** — evidence is sent to a registered department and enters their
review queue rather than sitting in a personal account.

**Police dashboard** — officers view, filter and manage submitted evidence in a dedicated
interface, with the review state recorded against each item.

**User-to-police messaging** — a built-in thread lets officers ask for clarification and lets
users respond, keeping the conversation attached to the case instead of scattered across inboxes.

**Access control and permissions** — role-based access separates citizens from police staff.
Authorisation is enforced server-side on every endpoint, never only hidden in the interface.

**Audit logs** — every action is recorded with actor, timestamp and target, giving accountability
that survives staff changes.

## Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Backend | Django, Python | Strong built-in auth and permission primitives, which is most of what a secure evidence system needs |
| Database | SQLite | Lightweight and appropriate for the deployment size, keeping the operational surface small for a non-technical team |
| Front-end | Tailwind CSS, JavaScript | Responsive layout and AJAX interactions without a framework overhead on a forms-heavy application |
| Dynamic UI | jQuery | AJAX-driven evidence submission and live status updates |

## Challenges and learnings

Secure file upload was the central problem. Accepting arbitrary files from the public internet
means validating type and content rather than trusting the extension, isolating storage from
execution, and never serving uploaded content in a way that lets it run. Layered validation,
restricted storage paths and serving every file as a download rather than inline removed most of
the risk — a lesson that shaped the storage layer completely.

Designing workflows was the second challenge, and the less technical one. The system had to be
genuinely easy for a stressed member of the public and equally clear for an officer reviewing
dozens of submissions. Every extra step produced drop-off, so the interface was reduced to the
minimum that kept evidence, context and consent together.

Audit logging turned out to be a design input rather than a feature to add at the end. Logging at
the model layer rather than in views meant no code path could quietly skip it, which is a
guarantee that view-level logging cannot offer.

## Outcome

Delivered in **April 2024**. Evidence submission moved from scattered file transfers into a
reviewable process, communication stayed attached to the case, and every action on every piece of
evidence is traceable — improving cooperation between the public and law enforcement without
weakening data protection.
