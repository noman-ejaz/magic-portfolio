## The problem

Restaurants that write their menu by hand lose the one piece of data that actually tells them
what to cook. Order history is the signal — but it is buried in paper, WhatsApp threads and a
cash register nobody wants to open.

The client needed three things in one place: a menu they could change themselves, an honest
record of what was ordered, and recommendations that used that record instead of guesswork.

## What I built

A menu and order platform where the recommendation engine sits on top of the order data rather
than beside it. Every completed order feeds a customer preference profile, and that profile is
what drives the suggestions.

**Menu management** — restaurant staff create, edit and categorise dishes from a responsive
interface without touching the database. Availability toggles propagate to the customer view
immediately.

**Order tracking** — orders are recorded with their items, timestamps and totals. The data is
queryable from day one, which is what makes everything else possible.

**Personalised recommendations** — the engine scores dishes against a customer's own order
history and past preferences. Recommendations are explainable: every suggestion can be traced
back to the order that produced it.

**Analytics dashboard** — restaurant managers get live views of best sellers, slow movers and
demand trends, rather than a static export they have to interpret themselves.

**Cloud-hosted backend** — the service runs on AWS with Supabase handling authentication and
real-time updates, so prices and availability change without a refresh.

## Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Front-end | Next.js, TypeScript | Server rendering for fast first paint, TypeScript to keep the recommendation logic safe as it grows |
| Backend | Supabase | Authentication and real-time order updates without maintaining an auth service |
| Database | PostgreSQL | Order history needs real relational queries; recommendations depend on aggregating over them |
| Cloud | AWS | Hosting, storage and scaling so peak ordering hours do not degrade the experience |

## Challenges and learnings

The hard part was performance. A naive recommendation query re-scanned the whole order table on
every menu load, which is fine with a hundred orders and unusable with fifty thousand. Moving
the scoring into indexed queries and pre-computing customer preference profiles brought the
response back to interactive range.

Integrating Supabase and AWS cleanly was the second challenge. Two services, two auth models and
two sets of environment variables is a reliable source of subtle bugs. Pinning down a single
source of truth for the session early — and treating the ORM layer as the only thing that talks
to the database — removed an entire category of problems.

## Outcome

Delivered in **November 2025**. The restaurant now runs its own menu without developer help,
sees which dishes actually sell, and gets suggestions grounded in real customer behaviour rather
than intuition. Order handling moved out of a manual process and into a system the business can
measure.
