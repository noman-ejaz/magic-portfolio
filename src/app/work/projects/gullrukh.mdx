## The problem

An off-the-shelf store was being asked to do things it was not designed for: pricing rules that
depend on combinations of attributes, and inventory that had to stay accurate across several
sales channels at once. Every workaround added another plugin, and the storefront was getting
slower with each one.

The client wanted a platform built around their actual catalogue rules rather than a template
fitted to them.

## What I built

A Flask eCommerce application where the product model is the source of truth for both the
storefront and the admin panel.

**Product management with variants** — products carry variants across size, colour and price, with
rules applied at the variant level rather than as special cases in the interface.

**Filtering and search** — customers narrow the catalogue by attributes, and results reflect the
same indexed data the admin panel edits, so the storefront can never disagree with the inventory.

**Cart and checkout** — cart state is server-side, which keeps pricing correct across devices and
survives a shared link.

**Order and inventory management** — stock levels and order statuses update together. Stock cannot
be sold twice, and every transition is auditable.

**Admin dashboard** — products, users, orders and configuration managed from one custom panel
rather than a host of plugins.

**Secure authentication** — login, session handling and permission boundaries reviewed explicitly,
because an admin panel is the highest-value target on an eCommerce system.

## Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Backend | Flask, Python | Lightweight and explicit routing suits a request-response storefront, without framework machinery the project does not need |
| Database | PostgreSQL | Product variants and stock are relational data with strict integrity requirements |
| Front-end | Bootstrap | Consistent responsive components across catalogue, cart and a large admin surface |

## Challenges and learnings

The main difficulty was schema design for variants. The first model flattened every attribute
into its own column, which broke the moment the catalogue needed a third variation axis. Moving to
a proper variant and attribute-value structure took longer up front and paid for itself
immediately — adding a new axis became configuration instead of a migration.

Query performance was the second problem. Filtering across several attributes produced a join per
filter, and unindexed it degraded quickly as the catalogue grew. Composite indexes on the filter
columns and a denormalised read view for the catalogue page fixed it without giving up
correctness at write time.

Cart handling taught the most about correctness under concurrency. Moving cart state to the server
and making checkout a single transaction, rather than several optimistic updates, eliminated the
double-spend class of bugs entirely.

## Outcome

Delivered in **early 2025**. The business runs its own catalogue and pricing rules without plugin
workarounds, storefront pages stay fast as the range grows, and the admin panel covers the
operations the previous stack could not.
