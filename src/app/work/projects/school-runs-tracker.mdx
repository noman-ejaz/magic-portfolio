## The problem

Schools running multiple vehicles relied on phone calls. A parent asks where the bus is, someone
calls the driver, the driver answers if they are not driving. Nobody could answer "how late are
we?" without starting a chain of phone calls, and no school had a record of pickups over time.

The brief was to make it behave like a taxi dispatch system, but for school transport: live
vehicle positions, assigned routes, and automatic notification when something changes.

## What I built

A dispatch platform where the vehicle position is the primary object. Everything else — route
assignment, pickup confirmation, delay alerts — is derived from it.

**Live vehicle tracking** — drivers report GPS position from the browser, and administrators see
every active vehicle on one map. No dedicated hardware, so adoption did not depend on the school
buying new vehicles.

**Route management and optimisation** — students are assigned to routes, and the route can be
rebuilt when a driver, vehicle or stop changes. Stops are ordered to reduce unnecessary driving
time.

**Student and driver records** — a single source of truth for enrollment, assigned drivers and
pickup and drop-off schedules, with history retained per term.

**Notifications and alerts** — arrival, delay and route-change alerts go out automatically to
parents and administrators. This is what replaced the phone-call chain.

**Mapping integration** — Google Maps for tiles and geocoding, HERE Maps as a fallback for routing,
so a single provider outage degrades the map instead of losing the feature.

**Background task automation** — Celery workers handle notification delivery and route
recalculation off the request cycle, so a slow map provider never blocks an administrator.

## Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Backend | Django, Django REST Framework | Mature ORM for the relational schedule data, plus a clean API surface for a separate front-end |
| Front-end | React, Next.js | Interactive live map and dispatch dashboard that updates without full page reloads |
| Database | PostgreSQL | Route, student and driver relationships are genuinely relational and need integrity constraints |
| Real-time | Firebase | Push updates to parents without holding long-lived connections open |
| Task queue | Celery, Redis | Notifications and route recalculation run in the background with retries |
| Cloud | AWS, Render | Separate hosting for the API and the front-end, so each scales on its own axis |

## Challenges and learnings

Real-time was the defining constraint. Tracking many vehicles at once while keeping latency low
meant deciding early what happens on the server and what happens in the browser. Pushing the
recomputation into Celery and only shipping the result over the API kept the request path short —
an early version did that work inline and stalled under realistic load.

Running Celery with Redis in production took more care than the code itself. Separate worker and
beat processes, a dead-letter path for failed jobs, and idempotent task handlers were all
necessary before notifications became reliable rather than mostly working.

Routing through two mapping providers added complexity but proved its worth: the fallback meant a
provider outage degraded navigation instead of taking down tracking.

## Outcome

Delivered in **September 2025**. The school gained a single live view of its fleet, parents get
arrival information without phoning the office, and the operations team spends its time on
exceptions rather than status updates.
